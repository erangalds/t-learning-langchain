# LLM Call Router Architecture Pattern

This script demonstrates a more sophisticated agent architecture using LangGraph, specifically an "LLM Call Router." The core idea is to use a Large Language Model (LLM) to first determine the category or domain of a user's query. Based on this routing decision, the agent then proceeds down a specific path, which might involve retrieving information from a domain-specific knowledge base and then using another LLM call to generate a final answer.

Let's break down the code:

1. Imports:

    + typing.Annotated, typing.Literal, typing.TypedDict: For defining structured data types for the graph's state, input, and output. Literal is used to specify that a value must be one of a few specific string options (e.g., "records" or "insurance").
    + langchain_core.documents.Document: Represents a piece of text, often with associated metadata. Used here for sample documents.
    + langchain_core.messages.HumanMessage, langchain_core.messages.SystemMessage: Core Langchain message types.
    + langchain_core.vectorstores.in_memory.InMemoryVectorStore: A simple vector store that holds data in memory, used for document retrieval.
    + langchain_ollama.ChatOllama, langchain_ollama.OllamaEmbeddings:
        + ChatOllama: The Langchain integration for Ollama LLMs.
        + OllamaEmbeddings: Used to generate numerical vector representations (embeddings) of text, necessary for semantic search in vector stores. The "nomic-embed-text" model is used for embeddings.
    + langgraph.graph.END, langgraph.graph.START, langgraph.graph.StateGraph: Core LangGraph components.
    + langgraph.graph.message.add_messages: Helper for updating message lists in the state.

3. Embeddings and Model Initialization:

    ```python
    embeddings = OllamaEmbeddings(model="nomic-embed-text")
    model_low_temp = ChatOllama(model="gemma3:27b", temperature=0)
    model_high_temp = ChatOllama(model="gemma3:27b", temperature=0.7)
    ```

    + embeddings: An instance of OllamaEmbeddings is created to convert text (like document content or user queries) into vector embeddings for similarity search.
    + model_low_temp: An LLM instance with temperature=0. This is used for the routing decision, aiming for a deterministic and precise output (the domain name).
    + model_high_temp: An LLM instance with temperature=0.7. This is used for generating the final answer, allowing for more creative and natural-sounding responses.

4. State, Input, and Output Definitions:

    + State(TypedDict):

        ```python
        class State(TypedDict):
            messages: Annotated[list, add_messages]
            user_query: str
            domain: Literal["records", "insurance"]
            documents: list[Document]
            answer: str
        ```

        Defines the graph's internal state.
        + messages: Conversation history.
        + user_query: The initial user question.
        + domain: The domain identified by the router (either "records" or "insurance").
        + documents: A list of Document objects retrieved based on the domain and query.
        + answer: The final answer generated by the agent.

    + Input(TypedDict):

        ```python
        class Input(TypedDict):
            user_query: str
        ```

        Defines the expected input to the graph.

    + Output(TypedDict):

        ```python
        class Output(TypedDict):
            documents: list[Document]
            answer: str
        ```

        Defines the structure of the final output from the graph.

5. Sample Documents and Vector Store Setup:

    ```python
    sample_docs = [
        Document(page_content="Patient medical record...", metadata={"domain": "records"}),
        Document(page_content="Insurance policy details...", metadata={"domain": "insurance"}),
    ]
    medical_records_store = InMemoryVectorStore.from_documents(sample_docs, embeddings)
    medical_records_retriever = medical_records_store.as_retriever()
    insurance_faqs_store = InMemoryVectorStore.from_documents(sample_docs, embeddings)
    insurance_faqs_retriever = insurance_faqs_store.as_retriever()
    ```

    + sample_docs: A list of Document objects. In a real application, these would come from actual data sources. Note the metadata={"domain": ...} which is good practice but not directly used by the InMemoryVectorStore for filtering in this simple setup (it's more for context or if the vector store supported metadata filtering directly during retrieval).
    + Two separate InMemoryVectorStore instances are created, one for "medical_records" and one for "insurance_faqs". Both are initialized with the same sample_docs in this example, which is a simplification. In a real scenario, each store would contain documents relevant to its specific domain.
    + .as_retriever(): Converts each vector store into a retriever object, which can be used to find documents similar to a given query.

6. Prompt Definitions:

    + router_prompt:

        ```python
        router_prompt = SystemMessage(
            """You need to decide which domain to route the user query to. You have two domains to choose from:
        - records: contains medical records of the patient, such as diagnosis, treatment, and prescriptions.
        - insurance: contains frequently asked questions about insurance policies, claims, and coverage.

        Output only the domain name."""
        )
        ```


        A SystemMessage instructing the model_low_temp LLM how to act as a router: classify the user query into "records" or "insurance" and output only the domain name.

    + medical_records_prompt and insurance_faqs_prompt: System messages to guide the model_high_temp LLM when generating answers for the "records" and "insurance" domains, respectively.


7. Node Definitions:

    + router_node(state: State) -> State:

        ```python
        def router_node(state: State) -> State:
            user_message = HumanMessage(state["user_query"])
            messages = [router_prompt, *state["messages"], user_message]
            res = model_low_temp.invoke(messages)
            return {
                "domain": res.content, # Expecting "records" or "insurance"
                "messages": [user_message, res],
            }
        ```

        This node performs the routing.
        1. Takes the user_query from the state.
        2. Calls model_low_temp with the router_prompt and the user query.
        3. Updates the state with the identified domain (the LLM's response content) and adds the user query and router's decision to the messages history.
    + pick_retriever(state: State) -> Literal["retrieve_medical_records", "retrieve_insurance_faqs"]:

        ```python
        def pick_retriever( state: State) -> Literal["retrieve_medical_records", "retrieve_insurance_faqs"]:
            if state["domain"] == "records":
                return "retrieve_medical_records"
            else:
                return "retrieve_insurance_faqs"

        ```

        This is a conditional edge function. It doesn't modify the state directly but returns the name of the next node to execute based on the domain in the current state.

    + retrieve_medical_records(state: State) -> State:

        ```python
        def retrieve_medical_records(state: State) -> State:
            documents = medical_records_retriever.invoke(state["user_query"])
            return {"documents": documents}
        ```    

        + If the router chose "records", this node is called. It uses the medical_records_retriever to fetch relevant documents based on the user_query and updates the state with these documents.
        + retrieve_insurance_faqs(state: State) -> State: Similar to retrieve_medical_records, but uses the insurance_faqs_retriever.
        + generate_answer(state: State) -> State:
        
            ```python
            def generate_answer(state: State) -> State:
                if state["domain"] == "records":
                    prompt = medical_records_prompt
                else:
                    prompt = insurance_faqs_prompt
                messages = [
                    prompt,
                    *state["messages"],
                    HumanMessage(f"Documents: {state['documents']}"),
                ]
                res = model_high_temp.invoke(messages)
                return {
                    "answer": res.content,
                    "messages": res,
                }
            ```

            This node generates the final answer.
            1. Selects the appropriate prompt (medical_records_prompt or insurance_faqs_prompt) based on the state["domain"].
            2. Constructs a message list including this domain-specific prompt, the conversation history (state["messages"]), and the retrieved state["documents"].
            3. Calls model_high_temp to generate the answer.
            4. Updates the state with the answer and adds the LLM's final response to the messages history.

8. Graph Construction:

    ```python
    builder = StateGraph(State, input=Input, output=Output)
    builder.add_node("router", router_node)
    builder.add_node("retrieve_medical_records", retrieve_medical_records)
    builder.add_node("retrieve_insurance_faqs", retrieve_insurance_faqs)
    builder.add_node("generate_answer", generate_answer)

    builder.add_edge(START, "router")
    builder.add_conditional_edges("router", pick_retriever) # Key part!
    builder.add_edge("retrieve_medical_records", "generate_answer")
    builder.add_edge("retrieve_insurance_faqs", "generate_answer")
    builder.add_edge("generate_answer", END)

    graph = builder.compile()
    ```

    + Nodes are added as usual.
    + builder.add_edge(START, "router"): The graph starts by executing the router node.
    + builder.add_conditional_edges("router", pick_retriever): This is crucial. After the router node executes, the pick_retriever function is called. The string returned by pick_retriever (e.g., "retrieve_medical_records") determines which node the graph transitions to next.
    + The subsequent add_edge calls define that after either retrieval node, the graph proceeds to generate_answer, and finally to END.
    + The flow is: START -> router -> (conditional based on pick_retriever)
        + If "records": -> retrieve_medical_records -> generate_answer -> END
        + If "insurance": -> retrieve_insurance_faqs -> generate_answer -> END

9. Using the Graph (Execution and Output Streaming):

    ```python
    input_data = {"user_query": "Am I covered for COVID-19 treatment?"}
    for i, chunk in enumerate(graph.stream(input_data)):
        if "router" in chunk:
            print("\n\nRouter Output:\n")
            print(chunk["router"]["domain"])
        if "generate_answer" in chunk:
            print("\n\nFinal Output:\n")
            print(chunk["generate_answer"]["answer"])
    ```

    + The graph is invoked with a sample user_query.
    + The graph.stream() method yields results as each node completes.
    + The loop prints the output from the router node (the chosen domain) and the generate_answer node (the final answer) as they become available.

In Summary:

This script creates an agent that can:

1. Route Queries: Use an LLM to classify a user's query into predefined domains ("records" or "insurance").
2. Conditional Retrieval: Based on the identified domain, retrieve relevant documents from a domain-specific vector store.
3. Contextual Answer Generation: Use another LLM, along with the retrieved documents and conversation history, to generate a final answer tailored to the query's domain.

This architecture is powerful because it allows the agent to handle different types of queries more effectively by directing them to specialized knowledge sources and processing paths. The use of conditional edges in LangGraph is key to implementing this routing logic.
