# Chain of LLM calls architecture pattern

This script demonstrates a "chain of LLM calls" architecture using LangGraph. The core idea is to have multiple, sequential interactions with Large Language Models (LLMs), where the output of one LLM call becomes part of the input for the next. In this specific example, the script first uses an LLM to generate an SQL query based on a user's natural language question, and then uses another LLM (or the same LLM with a different prompt/configuration) to explain the generated SQL query.

Here's a breakdown of the code:

1. Imports:

    + `typing.Annotated`, `typing.TypedDict`: For defining structured data types for the graph's state, input, and output.
    + `langchain_core.messages.HumanMessage`, `langchain_core.messages.SystemMessage`: Core Langchain message types. `HumanMessage` represents user input, and `SystemMessage` is used to provide instructions or context to the LLM.
    + `langchain_ollama.ChatOllama`: The Langchain integration for using Ollama to run LLMs locally (model "gemma3:27b" in this case).
    + `langgraph.graph.END`, `langgraph.graph.START`, `langgraph.graph.StateGraph`:` Core components from LangGraph for building stateful graphs.
    + `langgraph.graph.message.add_messages`: A helper to append new messages to a list in the state, crucial for maintaining conversation history.

2. visualize_graph Function:

    ```python
    def visualize_graph(graph, filename="graph.png"):
        # ... (implementation) ...
    ```

    + This is a utility function, identical to the one in 01-single-llm-call-architecture.py.
    + It takes a compiled LangGraph graph object and a filename.
    + It attempts to generate a PNG image visualizing the graph's structure using `graph.get_graph().draw_mermaid_png()`.
    + It includes error handling for missing dependencies (like `langgraph[draw]`) needed for visualization.

3. Model Initialization:

    ```python
    model_low_temp = ChatOllama(
        model="gemma3:27b",
        temperature=0,
    )
    model_high_temp = ChatOllama(
        model="gemma3:27b",
        temperature=0.7,
    )
    ```

    + Two instances of ChatOllama are created, both using the "gemma3:27b" model.
    + `model_low_temp`: Configured with `temperature=0`. This makes the LLM's output more deterministic and focused. It's suitable for tasks where precision is key, like generating an SQL query.
    + `model_high_temp`: Configured with `temperature=0.7`. This allows for more creativity and variability in the LLM's output. It's suitable for tasks like generating a human-like explanation of the SQL query.

4. State, Input, and Output Definitions:

    + State(TypedDict):

        ```python
        class State(TypedDict):
            messages: Annotated[list, add_messages]
            user_query: str
            sql_query: str
            sql_explanation: str
        ```    

        + Defines the overall data structure that will be passed between nodes and updated throughout the graph's execution.
            + `messages`: A list to store the conversation history (human messages, AI responses). add_messages ensures new messages are appended.
            + `user_query`: The initial natural language question from the user.
            + `sql_query`: The SQL query generated by the first LLM call.
            + `sql_explanation`: The explanation of the SQL query generated by the second LLM call.

    + Input(TypedDict):

        ```python
        class Input(TypedDict):
            user_query: str
        ```

        + Defines the expected structure of the initial input to the graph. The graph will be started with a dictionary containing just the `user_query`.

    + Output(TypedDict):

        ```python
        class Output(TypedDict):
            sql_query: str
            sql_explanation: str
        ```    

        + Defines the structure of the final output from the graph. The graph will return a dictionary containing the generated `sql_query` and `sql_explanation`.

5. Prompt Definitions:

    + generate_prompt:

        ```python
        generate_prompt = SystemMessage(
            "You are a helpful data analyst, who generates SQL queries for users based on their questions.The output should be a valid SQL query. "
            "The SQL query should be in the format of a string, and should not contain any additional text or explanations. "
        )
        ```

        A `SystemMessage` that instructs the first LLM (`model_low_temp`) on how to behave: act as a data analyst, generate SQL from user questions, and output only the SQL query as a string.

    + explain_prompt:

        ```python
        explain_prompt = SystemMessage(
            "You are a helpful data analyst, who explains SQL queries to users."
        )
        ```

        A `SystemMessage` that instructs the second LLM (`model_high_temp`) to act as a data analyst and explain SQL queries.

6. Node Definitions:

    + generate_sql(state: State) -> State:

        ```python
        def generate_sql(state: State) -> State:
            user_message = HumanMessage(state["user_query"])
            messages = [generate_prompt, *state["messages"], user_message]
            res = model_low_temp.invoke(messages)
            return {
                "sql_query": res.content,
                "messages": [user_message, res],
            }
        ```

        This function defines the first main processing node in the graph.
        1. It takes the current state as input.
        2. Extracts `state["user_query"]` and wraps it in a `HumanMessage`.
        3. Constructs a list of messages to send to the LLM:
            + The generate_prompt (system instruction).
            + Any existing messages from `state["messages"]` (though in this specific flow, `state["messages"]` will be empty when this node is first called if the graph starts with only user_query in the input dictionary).
            + The new user_message.
        4. Calls `model_low_temp.invoke(messages)` to get the SQL query.
        5. Returns a dictionary to update the state:
            + "`sql_query`": Set to the content of the LLM's response (the generated SQL).
            + "`messages`": Updates the conversation history by adding the user_message and the LLM's response (res).

    + explain_sql(state: State) -> State:

        ```python
        def explain_sql(state: State) -> State:
            messages = [
                explain_prompt,
                *state["messages"],
            ]
            res = model_high_temp.invoke(messages)
            return {
                "sql_explanation": res.content,
                "messages": res,
            }
        ```

        This function defines the second main processing node.
        1. It takes the current state (which now includes the `sql_query` and updated `messages` from the `generate_sql node`).
        2. Constructs a list of messages:
            + The explain_prompt (system instruction for explanation).
            + The current `state["messages"]`. This is important because `state["messages"]` now contains the original user query and the generated SQL query (as an AI message). This provides context to the `model_high_temp` for generating the explanation.
        3. Calls `model_high_temp.invoke(messages)` to get the SQL explanation.
        4. Returns a dictionary to update the state:
            + "`sql_explanation`": Set to the content of the LLM's response (the explanation).
            + "`messages`": Appends the LLM's explanation response to the conversation history.

7. State Graph Construction:

    ```python
    builder = StateGraph(State, input=Input, output=Output)
    builder.add_node("generate_sql", generate_sql)
    builder.add_node("explain_sql", explain_sql)
    builder.add_edge(START, "generate_sql")
    builder.add_edge("generate_sql", "explain_sql")
    builder.add_edge("explain_sql", END)
    ```

    + `builder = StateGraph(State, input=Input, output=Output)`: Initializes the `StateGraph`.
        + `State`: Specifies the internal state structure.
        + `input=Input`: Specifies the expected format of the initial input to the graph. When the graph is invoked, the input dictionary (matching Input) will be merged into the initial State.
        + `output=Output`: Specifies the format of the final output from the graph. Only the keys defined in Output will be returned from the final state.
    + `builder.add_node(...)`: Registers the `generate_sql` and `explain_sql` functions as nodes in the graph.
    + `builder.add_edge(...)`: Defines the directed connections (edges) between nodes, creating a linear flow:
        1. `START` -> `generate_sql`: The graph execution begins and immediately calls the `generate_sql` node.
        2. `generate_sql` -> `explain_sql`: After `generate_sql` completes, the graph proceeds to the `explain_sql` node.
        3. `explain_sql` -> END: After `explain_sql` completes, the graph execution terminates.

8 Compiling the Graph:

    ```python
    graph = builder.compile()
    ```

    This compiles the defined nodes and edges into an executable graph object.

9. Using the Graph (Execution and Output):

    ```python
    result = graph.invoke({"user_query": "What is the total sales for each product?"})
    print("\nFull result:")
    print(result)
    print('\n\nSQL query:\n')
    print(result['sql_query'])
    print('\n\nSQL explanation:\n')
    print(result['sql_explanation'])
    ```

    + `graph.invoke({"user_query": "..."})`: Executes the compiled graph.
        + The input dictionary `{"user_query": "..."}` matches the Input `TypedDict`. LangGraph will take this user_query and place it into the initial State object that the `generate_sql` node receives.
        + The graph runs through the sequence: `generate_sql`-> `explain_sql`.
        + The invoke method waits for the entire graph to complete and returns the final output, which will be a dictionary matching the Output `TypedDict` (containing sql_query and sql_explanation).
    + The script then prints the full result dictionary and the individual `sql_query` and sql_explanation values.

10. Graph Visualization Call:

    ```python
    output_filename = "05-agent-architecture-01/02-chain-of-llm-calls-architecture.png"
    visualize_graph(graph, output_filename)
    ```

    Calls the visualize_graph function to save a PNG image of the graph's structure. The image would show: [START] --> generate_sql --> explain_sql --> [END].

In Summary:

This script creates a two-step LLM agent:

1. Step 1 (SQL Generation): Takes a user's natural language question, uses an LLM (model_low_temp) with a specific prompt to convert it into an SQL query.
2. Step 2 (SQL Explanation): Takes the generated SQL query (and the original user question as context), uses another LLM configuration (model_high_temp) with a different prompt to generate a natural language explanation of what the SQL query does.

The LangGraph framework manages the state (including conversation history, the generated SQL, and its explanation) and orchestrates the flow between these two LLM-powered nodes. This "chaining" allows for more complex tasks to be broken down into manageable, sequential steps, with each step potentially using a differently configured or prompted LLM best suited for that sub-task.
